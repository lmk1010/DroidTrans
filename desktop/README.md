# desktop — DroidTrans（Go）

一个二进制：HTTP `9500` + TCP `9501` + FTP `9502`，内嵌界面。不再使用 Flask / Python / Tauri。

```bash
cd desktop
chmod +x build.sh
./build.sh
./../dist/droidtrans          # 打开界面
./../dist/droidtrans -headless # 只听端口
```

macOS 会生成 `dist/DroidTrans.app`。钥匙串里有 Developer ID 证书时自动签名；
再配一份公证凭据（`xcrun notarytool store-credentials droidtrans --apple-id <你的 Apple ID> --team-id 24D88Q3K3S --password <App 专用密码>`），打包时会自动公证并装订票据。
两者都没有时产出的是未签名的开发构建，Gatekeeper 会拦，需要 `xattr -cr /Applications/DroidTrans.app`。

## ATF3 线协议

高速通道（TCP 9501）的帧格式。三份实现：`internal/fast/fast.go`（服务端）、
`ios/DroidTrans/Core/FastSender.swift`、`android/.../FastTransferClient.java`。

```
客户端 → 服务端   "ATF3" | tokenLen u32 | token | nameLen u32 | name | size u64
服务端 → 客户端   0x00 | offset u64      从第 offset 字节开始发
                 0x01 | msgLen u32 | msg  拒绝（令牌不对、盘满、路径非法…）
客户端 → 服务端   offset .. size 的原始字节
服务端 → 客户端   0x02                    收完并落盘成功
                 0x01 | msgLen | msg      出错
```

握手那一次往返就是断点续传的全部代价。**必须在客户端发任何文件字节之前完成**，
否则「续传」就退化成「传完再丢掉重复的部分」，一点带宽都省不下来。

应答是二进制而不是以前的 `OK\n` / `ERR ...\n` 文本：偏移量是 8 字节大端，
里面出现 `0x0A` 完全正常，按换行切会把一个数字劈成两半 ——
这种 bug 只在特定文件大小下复现。

ATF1（无令牌）和 ATF2（无偏移协商）已经删除，服务端不再接受。

### 落盘纪律

没传完的字节永远写在 `.<文件名>.<大小>.dtpart` 里，**绝不出现在目标路径上**。
半个文件躺在输出目录里比传输失败更糟 —— 用户不知道它是坏的。
写满 size 字节才 `rename` 转正，同分区上的 rename 是原子的。

分片名里带总大小，是为了让「同名但不是同一个文件」自然拿到不同的分片。
相册里同名文件遍地都是，按文件名续传迟早续错。

### 改了线格式要跑什么

```bash
ios/Tools/atf3vec/run.sh          # 重新生成跨语言对拍向量
cd desktop && go test ./internal/fast/
```

后者会用服务端真正在用的 `readHeader` 去解析 Swift 生成的字节。
各端自己的单测只能证明「自己和自己一致」，字段错位要靠这道对拍才拦得住。

## 从照片图库救数据（internal/photoslib）

绕开「照片」App 的导出器，直接读图库的 `Photos.sqlite`，按记录去 `originals/`
取原始文件，用**用户认识的文件名**（`ZORIGINALFILENAME`，比如 IMG_1234.HEIC，
而不是图库内部那串 UUID）按年月摊成普通文件夹。全程只读图库。

```
输出目录/照片图库/2026/2026-09/IMG_1234.HEIC
                                IMG_1234.MOV   ← 实况照片的动态部分，同名
```

### 三件必须记住的事

**一、本机很可能根本没有原片。** 开了 iCloud「优化储存空间」之后，本地只有
缩略图。开发机上实测：70 条记录里 69 条本地没有原文件。**这个数字必须显式
报给用户**，静默导出剩下那几张就说完事了，正是我们要取代的那种烂体验。

**二、库是锁着的，而且是 WAL 模式。** 照片 App 开着的时候直接开库会失败；
只复制主库文件会读到几小时前的旧数据，用户刚导入的照片凭空消失。
`-wal` 和 `-shm` 必须一起复制走，让 SQLite 自己回放。

**三、schema 会随 macOS 版本变。** 这是这类工具的长期维护成本，认了。
查询失败时给的是「图库结构和预期不符（macOS 版本可能太新或太旧）」，
不是把 SQL 错误直接抛给用户。

### 权限

图库在 TCC 保护下。读不到时报的是「到系统设置 → 隐私与安全性 →
完全磁盘访问权限里把卓传打开」，而不是 `operation not permitted`。

### 图库不止一个

只认默认位置（`~/Pictures/Photos Library.photoslibrary`）是不够的：
**照片一多，图库就会被搬到外置硬盘上，而照片多的人恰恰最可能为这个功能付钱。**
`Discover()` 会翻家目录常见位置和所有挂载的卷，把找到的列出来让用户挑 ——
不是给个输入框让他粘路径，大多数人不知道 `.photoslibrary` 是个
「伪装成文件的文件夹」，在访达里根本点不进去。

只找到一个（绝大多数人）就整块不显示，多一步选择对他们是纯负担。

判断是不是图库要看里面有没有 `Photos.sqlite`，光看后缀不够 ——
半个拷贝过来的空壳会一直到扫描时才失败，用户会以为是我们的 bug。

体积只算 `originals`：图库里还有一大堆缩略图和渲染缓存，
算进去用户对「能导出多少」的预期就是错的。

### 性能

五万条记录的库，扫描实测 **200ms**（`TestScanBigLibrary` 会一直盯着）。
所以扫描保持同步，没必要为它加一套异步任务。这个数字是量出来的不是估的 ——
之前担心「大库会不会卡死」，量完发现不是问题。

### 文案

这是商业产品，用产品语言，不要口语随笔。第一版写成了「把原片救出来」
「摊成普通文件夹」「挑单张」「导完了」这种腔调，得改。对照：

| 别这么写 | 这么写 |
| --- | --- |
| 把照片图库里的原片救出来 | 照片图库导出 |
| 先扫一遍，看看有多少原片在这台电脑上 | 扫描后可查看本机可导出的项目数量 |
| 挑单张 | 逐项选择 |
| 导完了：1 张，存在 xxx | 导出完成 · 1 个项目 · xxx |
| 有 69 张只在 iCloud 上…要它们的话… | 69 个项目仅存于 iCloud…请在「照片」中开启… |

导航标签也别撞车：这一页叫「照片图库」，接收记录那一页原来也叫「图库」，
两个都叫图库用户分不清 —— 后者已改名「已接收」，本来它显示的也不是图库，
是别的设备传过来的东西。

### 界面

**这一页是全平的，跟 Wi-Fi / USB 页一样：不套卡片、不加边框、不投影。**
这套界面是刻意压平过的 —— `.path-row`、`.listen` 都显式把 `background`、
`border-radius`、`box-shadow` 关掉，`border: 0` 是全局规则。
第一版我给整块内容包了一层带边框的圆角容器，四个数字又各是一张小卡片，
两层卡片摞着，和周围完全不是一个东西。改回来了：
四个数字就是四组数字，靠颜色（只在 iCloud 是橙的）跳出来而不是靠盒子；
「导到哪里」直接复用 Wi-Fi 页那个 `.path-row`，不另造一套输入框。

加新东西之前先看隔壁页怎么摆的，别自己发明。

入口有两处：侧栏「**Mac 照片**」和总览页的第二块。侧栏刻意不叫「照片图库」——
下面还有一个「图库」（收到的文件），两个都叫图库用户分不清。

结果页上最重要的不是「导出」按钮，是那个橙色的「**只在 iCloud**」计数。

**挑单张**：网格默认全选、逐张取消。前端只记「排除了谁」（`excluded`）
而不是「选了谁」—— 五万张的库光 uuid 就近 2MB，为了取消两张
把它们全塞进请求体没道理。用户点过「全不选」之后才切成 `selected`。
后端两种都收。

缩略图走 `qlmanage`（HEIC 和视频都吃）并缓存，接口只认扫描结果里的 UUID ——
收任意路径的话，这就成了一个「把本机任意文件读出来」的接口。

### 免费 / Pro 的分界

**扫描免费，导出才要 Pro。** 用户得先看见「你这库里 3421 张在本机、
1892 张只在 iCloud」，才知道这功能对他有没有用。上来就挡在付费墙后面
等于让人盲买。


## 导航结构

按「跟谁打交道」分组，不按传输方式罗列：

```
总览
手机          USB 导入      数据线 · 仅安卓
             Wi-Fi 传输    无线 · 双向
这台电脑      照片图库      导出原始文件
             已接收        传过来的文件
```

**每一项都要标出适用场景。** USB 走 ADB，只支持安卓；iPhone 只能走 Wi-Fi。
这个约束不写出来，用户只能挨个点进去试 —— 而这正是「功能多、不知道怎么用」
的来源：导航按技术手段分，等于让用户替我们做技术决策。

「照片图库」是唯一一个不涉及手机的功能，必须和传输分在不同组里，
否则会被当成又一种传输方式。

三条一致性要求：

1. **侧栏和总览的分组、顺序、标签必须一样。** 两处不一致，用户就会建立两套心智模型。
2. **页面标题和侧栏标签必须一样。** 侧栏写「USB 导入」、点进去标题是「USB」，
   像是换了个地方。
3. **同一个设置只能有一套说法。** 「接收位置」在 USB 和 Wi-Fi 两页都出现，
   但 `wifiSetOut` 同时写 `wifiOut` 和 `OutputDir`，它是一个设置 ——
   所以两处都注明「USB 与 Wi-Fi 共用此位置」，否则看起来像两个互不相干的选项。


## 免费额度

收费点建在「量」上，不建在「功能种类」上 —— 这是这个品类的通行做法，
不是我们发明的：

| | 免费额度 | 依据 |
| --- | --- | --- |
| 单个文件 | 4 GB | Send Anywhere 免费版单次上限 2 GB |
| 照片图库导出 | 1000 项 / 次 | PowerPhotos 付费解锁「无限量导出」 |

**4 GB 这个数字不能随便动。** iPhone 4K60 视频约 400 MB/分钟，
4 GB 正好是 10 分钟 —— 日常照片和短视频完全碰不到，碰到的是长录像、
录屏、电影、整包备份这类，那才是愿意付钱的人。

一度考虑过 2 GB，算完否掉了：2 GB 只有 5 分钟，随手拍段孩子的演出就超，
会砸在普通用户身上，违背「普通用户无感、需要的人才付费」这条原则。

### 两条底线

**局域网互传和断点续传永久免费不限量。** 正面对上 LocalSend，
在传输本身上收费只会把人推走。额度卡在「大文件」和「批量导出」上，
那是 LocalSend 根本没有的场景。

**拒绝要发生在传输开始之前。** 文件大小在 ATF3 的头里就有，
握手那一步就该给出结论 —— 传到 3 GB 才说「太大了」是最糟的做法。
超额用的是独立的状态字 `statusUpgrade (0x03)` 而不是普通错误，
客户端才能给出升级入口；混在错误里，用户只会以为传输坏了。

### 超额必须提前告知

**在用户按下「开始」之前就把结论给出来，不是跑到一半停下来。**
跑一半才停的话，用户已经等完了，还得自己想明白该再点一次 —— 这是最招骂的做法。

两处都做了：

- **照片图库导出**：扫描时就知道选了多少、额度多少，超了就在按钮上直接写
  「导出 1000 项」而不是含糊的「开始导出」，旁边给出剩余数量和升级入口。
- **手机端相册同步**：`/api/wifi/info` 和 `/api/health` 都会带上 `max_file_size`，
  手机扫描相册时就把超额的挑出来单独报，不混进待传列表 ——
  混进去的话进度会卡在某一张上反复失败，看着像坏了。

### 额度为什么是 1000 不是 200

200 张只是一次旅行的量，普通用户一趟就用完，那不叫「体验过」，
叫「刚上手就被拦住」。1000 张够一个人把最近一两年的照片理出来，
真正碰到上限的是整库几千上万张的人 —— 那才是该付费的人。

### 导出额度要能连续推进

免费导出数的是「真正抄过去的个数」，已存在被跳过的不算。
数成「处理过的个数」的话，用户第二次点导出时前 200 项全被跳过、
一个新的都不出来，看起来就是坏了。


## 付费页：已激活也要留着对比

激活之后**不要**把免费 / Pro 对照表换成一排勾。

那恰恰把最该强化价值的时刻浪费掉了：付了钱的人打开来，看到五个勾，
不知道自己比免费版多拿了什么。留着对照表，把 Pro 那一列标成「你的」、
免费列里被解除的额度划掉，他看到的是「免费只有 4 GB，我不限；
免费 1000 项，我不限」—— 这才是买到东西的感觉。

没有差额的行（局域网互传、断点续传）不划线：免费本来就有，
划掉会变成暗示「这些也是买来的」，不诚实。

三处必须说同一套规则：`ios/.../ProView.swift`、`desktop/frontend/app.js`
的 `LIC_COMPARE`、官网 `site/src/i18n/*.ts` 的 pricing。
改了额度记得三处一起改 —— 之前就出现过官网还在卖已经证实是假的
「自动归档」，而客户端早就撤掉了。


## 多设备

插着两台安卓机时，USB 页的设备名是个下拉：点开列出每一台的**型号 + 序列号**，
点一下切过去。只连一台时不显示箭头 —— 一个点不动的箭头是纯噪音。

后端 `/api/devices`、`/api/select_device` 一直都在，**但前端从来没调过**，
所以插两台机器时用户只看得到当前那台，另一台等于不存在。

### 三个不显然的地方

**型号要按序列号单独查。** `adb shell getprop` 走的是当前选中的设备，
拿它挨个问就得先 `SetSerial`，那会把用户正在用的选择改掉 ——
表现为「点开列表，当前设备就被换了」。用 `PropOf(serial, …)` 带 `-s` 直接问。

**序列号必须显示。** 两台同款手机型号字符串完全一样，只有序列号能区分。

**换设备必须清掉上一台的扫描结果。** `selectDevice` 现在会清空 `albums`、
重置扫描状态、递增 `scanID`。不清的话界面上还挂着上一台的相册，用户直接点
「开始传输」，拉的是旧设备上的路径 —— 轻则一片失败，重则从新设备上取到
同名的别的文件。`TestSelectDeviceClearsPreviousScan` 盯着这条。

`scanID` 递增也是必须的：切换时如果还有一个扫描在跑，它回来时会用旧结果
覆盖新设备的。
