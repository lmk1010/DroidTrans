# 手机互传

两台手机之间直接传，不经过电脑。安卓 ↔ 安卓、安卓 ↔ iPhone 都走同一套东西。

## 怎么连上的

现有协议是 HTTP：一侧当服务端，另一侧当客户端。两台手机之间没有天然的服务端，
所以这一屏第一件事就是问「这次你是发还是收」。

- **收的那台**跑起 `PeerServer`（默认 9600，被占用时退到系统分配的端口），
  用 NSD 广播和电脑同一个 `_droidtrans._tcp`，并显示一张二维码。
- **发的那台**走原来那套雷达/扫码流程，把对面当成一台「电脑」照常连 ——
  发送侧的代码一行都不用改。

配对不用抄码：发送方发一个不带码的 `POST /api/pair`（敲门），接收方弹一句
「XXX 想连过来」，点同意就通。六位码只是兜底，二维码里也带着它。

对面等人点头最多挂 45 秒，所以**发送方这条请求的超时必须放宽到 60 秒**
（iOS `ApiClient.pair`、Android `Pairing.knock`）。用默认的 8 秒，
表现是「对面明明点了同意，这边还是说连不上」。

## 没有路由器的时候

接收端的二维码里除了地址和配对码，还可以带上一个直连热点的 SSID 和密码
（格式见 `network/PeerLink.java` 与 iOS 的 `Core/PeerLink.swift`，两份必须一致）：

    http://192.168.49.1:9600/?c=123456&n=Pixel%207&s=DroidTrans-3f2&k=8a91c07b

- 接收端点「没有 Wi-Fi？开直连热点」：**先试 Wi-Fi Direct 自建组**
  （`DirectGroup`，Android 10 起），拒了才退到 **LocalOnlyHotspot**。
  顺序别倒过来，两个理由：
  1. **频段**。LocalOnlyHotspot 开在哪个频段完全由系统定，不少机型直接给
     2.4GHz，实测 5~8 MB/s —— 那还不如走路由器，「直连」两个字就没意义了。
     建 P2P 组可以请求 5GHz（`setGroupOperatingBand`）。
  2. **免扫码**。组主能在 P2P 上广播 DNS-SD 服务，那是预关联的，见下。
  组主本身就是普通 AP，所以 iPhone 也能加入 —— 它不需要懂 Wi-Fi Direct。
- 发送端扫到带 `s/k` 的码，直接替用户入网：安卓用 `WifiNetworkSpecifier`
  （连上后必须 `bindProcessToNetwork`，这个热点没有互联网，不绑的话
  请求会继续发到有网的那张卡上，全部打空）；iOS 用 `NEHotspotConfiguration`。

### 安卓对安卓：不用扫码

接收端建组之后还会在 P2P 上广播一个 DNS-SD 服务（`DirectGroup.advertise`）。
这一步是**预关联**的：对面还没连上任何网络就能发现它。局域网里那套
`NsdManager` 做不到 —— 它要求两台已经在同一个网里，而这条路存在的前提
恰恰是「没有网」。

发送端（`DirectFinder`）在「找设备」那一屏和 Bonjour 并行跑服务发现，
发现的手机直接进雷达；点一下走 `WifiP2pManager.connect()`，
**密码全程由系统在两端之间交换，用户一个字都看不到**，
连上之后组主地址就是接收端地址，后面照旧走 HTTP 那一套。

点之前会先 `WifiJoiner.release()` 把之前扫码入网留下的进程绑定松开 ——
绑着别的网卡的话，打给组主的请求会全发到那张卡上。

**这条只有安卓有。** iPhone 既不懂 Wi-Fi Direct，也没有扫描周围 Wi-Fi 的
能力，所以 iPhone 那一侧凭据只能靠二维码递过去，扫码对它是唯一的路。

**iOS 要 Hotspot Configuration 能力**：`DroidTrans.entitlements` 里已经写上，
还得在 Apple 开发者后台给这个 App ID 勾上，否则真机构建会卡在
「描述文件缺少该权限」。签不上时代码不会崩，只会退回「请手动连接 XXX」。

两台 iPhone 之间还有一条 **AWDL**：`includePeerToPeer = true`（监听和浏览两边都要开），
没有路由器也能互相看见。代价是那时候拿到的只有 `fe80::…%awdl0` 这种链路本地地址，
拼进 URL 必须写成 `[fe80::…%25awdl0]`，见 `urlHost`。

## 传输通道

手机接收端只实现了 `PUT /api/fast/put`（ATF3 裸流和 FTP 是桌面端才有的加速），
所以它在 `/api/fast/caps` 里只报 `http_put`。**发送方必须看这个 prefer 清单**：
安卓端 `ProtocolSelector` 早先探测超时就退到 `http_multipart`，
而手机端根本没有那个口 —— 结果是 404，用户看到「传输失败」。

断点续传两边都有：先 `GET /api/fast/offset` 问「你已经收到第几个字节」，
只补剩下的那段。没收完的字节躺在 `.<name>.<size>.dtpart` 里，收全了才改名。

## 跨平台对跑

协议有三份实现（Go / Java / Swift）。单端测试全绿而两端说不上话，是这套东西
最典型的故障形态，所以有一组用例让**安卓模拟器和 iOS 模拟器真的互相传一个文件**。
平时跑整套用例时它们自动跳过，需要外面有一台在等着才跑。

安卓发、iPhone 收：

```bash
echo > ~/.droidtrans-interop-serve            # iOS 侧的开关
cd ios && xcodebuild test -project DroidTrans.xcodeproj -scheme DroidTrans \
  -destination 'id=<模拟器 UDID>' \
  -only-testing:DroidTransTests/PeerInteropTests/testServesAnExternalSender &

# iOS 模拟器用的是宿主机的网络栈，所以模拟器里的 9600 就是 Mac 的 9600，
# 安卓模拟器从 10.0.2.2 就能到
cd android && ./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.mk.androidtransfer.network.PeerInteropTest#sendsFileToAnExternalPeer \
  -Pandroid.testInstrumentationRunnerArguments.peerHost=10.0.2.2
```

iPhone 发、安卓收：

```bash
echo 127.0.0.1:9600 > ~/.droidtrans-interop-peer
cd android && ./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.mk.androidtransfer.network.PeerInteropTest#servesAnExternalSender \
  -Pandroid.testInstrumentationRunnerArguments.serve=1 &
adb forward tcp:9600 tcp:9600            # 把模拟器里的接收端露给 Mac
cd ios && xcodebuild test-without-building ... \
  -only-testing:DroidTransTests/PeerInteropTests/testSendsToAnExternalPeer
```

iOS 侧的开关走宿主机 home 下的标记文件，不用环境变量：xcodebuild 的
`TEST_RUNNER_XXX` 只喂给 UI 测试的 runner 进程，App 内跑的单测收不到；
宿主机 home 的位置由模拟器通过 `SIMULATOR_HOST_HOME` 告诉进程。

**测不到的部分**：Bonjour 发现（模拟器的 NSD 出不了它那层 NAT）、直连热点、
Wi-Fi Direct、扫码自动入网、AWDL —— 这些要动真的射频，只能上真机。
